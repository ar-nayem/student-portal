# Moving student documents out of public storage

Student uploads now go into `storage/student-documents` under the app's working directory. Keep that directory persistent, writable by the app service account, and outside the web server's public root. The authenticated portal can read old files in `public/uploads` during preparation. Until those old files are moved, a previously shared raw URL can still bypass the portal's ownership check.

Before opening the assignment feature to production traffic:

1. Pause the app and other writers. Back up the SQLite database, `public/uploads`, `storage/student-documents`, and any existing `storage/unidentified-student-uploads` outside the web root. Confirm the database and paths point to the deployed instance.
2. From the deployed checkout, run `python3 scripts/move-student-documents.py /absolute/path/to/prisma/dev.db /absolute/path/to/checkout` as the app service account. The mover resolves the public, private, and quarantine paths and rejects aliases or overlaps. Review the quarantine list and resolve any missing files, unexpected directories or symlinks, shared document/message names, or mismatched copies it reports before proceeding.
3. Run the same command with `--apply`. It copies and verifies each file before removing the public copy and can be rerun after interruption. Referenced student documents go into `storage/student-documents`. Unidentified top-level files, including files left behind after a document or student was deleted, go into `storage/unidentified-student-uploads` for restricted review. Keep quarantined bytes outside the web root while their origin is established. The mover leaves the database, the `uploads/website` and `uploads/universities` directories, and attachments with the message uploader's root-relative `/uploads/<filename>` URLs in place. Review any legitimate public files or message URLs that use a different layout before applying the move.
4. Rerun without `--apply` and require zero documents to move, zero unidentified files to quarantine, and zero unresolved findings. Start the new app and verify an authorized user can open a migrated file and include it in a batch or backup ZIP. Check that old raw `/uploads` URLs for a migrated document and a quarantined file return 404 through the public hostname, and verify a website asset and message attachment still load. Purge any public static cache containing student attachment URLs. Confirm that callbacks and proxy aliases cannot expose private storage or quarantine.

If rollback is needed, keep traffic paused while rolling back the application and the database. Back up all new files and records first. An older release expects student documents under `public/uploads`, so restoring it with publicly accessible copies also restores the former exposure. Keep the student file URLs blocked at the proxy during a rollback or restore the release only with the application off the public network until a safe file serving path is available.
